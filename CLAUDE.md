# CLAUDE.md

Guidance for AI assistants (and humans) working in this repo. It's a learning project: follow
mainstream best practices, keep things simple, skip production hardening that doesn't teach anything.

## Repo map

| Path | What |
|---|---|
| `twitter-go-api/` | Primary backend: Go, Gin, PostgreSQL (sqlc, pgvector), optional Redis. See its README's "Where things live" table; the client contract is Swagger (`/swagger/index.html`, generated from handler annotations, never committed) plus the README's "API Behavior" rules. |
| `twitter-next-web/` | Next.js (App Router) frontend: TanStack Query, Tailwind v4, Radix/shadcn primitives. |
| `infra/` | AWS and monitoring as code (see `infra/README.md`): `terraform/{bootstrap,app}`, `compose/` (the host's stack), `observability/` (Prometheus, Alertmanager, Loki, Alloy, Grafana), `scripts/` (up, deploy, down). The stack only exists while the user brings it up: keep everything valid offline. |

## Commands

```bash
make                                       # list the root shortcuts below (they call the commands in each app)
make dev                                   # db, then api + web in one terminal (Ctrl+C stops both)
make db                                    # Postgres (pgvector, pg16), Redis, RustFS (S3-compatible media) for local dev
make db-reset                              # wipe local data and recreate (after editing the schema)
make monitoring                            # + local monitoring (Grafana :3001, Prometheus :9090)
make api                                   # API on :8080, migrations run at startup
make web                                   # web on :3000
make check                                 # check-api (vet + race tests), check-web, check-infra (terraform, shellcheck)
make gen                                   # after editing the SLO table or dashboard panels (CI checks they're up to date)
make infra-up / deploy / infra-down        # AWS stack (the user runs these)

# In twitter-go-api/
make test                                  # go test -race; integration tests need TEST_DATABASE_URL (see README)
make sqlc                                  # after editing internal/db/queries or migrations: regenerates code + MockStore
make swagger                               # regenerate the Swagger docs (run, lint and test already do)
```

Enable the pre-commit hook once per clone: `git config core.hooksPath .githooks`.

## Go API conventions

- **Package by feature.** `internal/<feature>/<feature>.go` exposes `Service` + `New(...)`, returns domain
  types, never imports Gin. Handlers in `internal/api/` only bind input, call a service and map to a DTO.
- **Every route is in `internal/api/routes.go`**, one line each, with its auth and rate-limit middleware.
- **Interfaces belong to the consumer** (`api/services.go`, or a small private interface in a feature).
- **Errors:** services return `apperr` kinds (`apperr.NotFound`, `Conflict`, …) or wrap DB errors with
  `db.NotFound(err, "thing")`; `api/errors.go` maps them to HTTP. Don't write status codes in services.
- **SQL lives in `internal/db/queries/*.sql`** and is generated by sqlc; never hand-edit `*.sql.go`.
  Lists use keyset cursors (`internal/pagination`), not OFFSET.
- **Schema:** data is disposable, so edit `000001_init_schema.up.sql` in place rather than adding migrations
  (`make db-reset` applies it locally).
- **Auth:** sessions are httpOnly cookies (`access_token`, `refresh_token`) set by the API. Stale
  credentials answer `401 TOKEN_EXPIRED`; no credentials answer `401 UNAUTHORIZED`. Refresh tokens are
  single-use (rotation). Cross-origin writes are blocked by `http.CrossOriginProtection`.
- **Logging:** `slog.InfoContext(ctx, …)` / `ErrorContext`; the request ID is added from `ctx` automatically.
- **Tests:** table-driven, next to the code they test (`tweet_handler.go` → `tweet_handler_test.go`);
  handler tests use the fakes in `api/fakes_test.go`; DB tests use `dbtest.OpenTestDB` and skip
  without `TEST_DATABASE_URL`.

## Web conventions

- **Query keys only from `src/lib/query-keys.ts`.** Never inline key arrays.
- **Optimistic updates go through `src/lib/query-cache.ts`** (`updateTweet`, `updateUser`,
  `removeFeedItems`): one call updates every cached copy, whatever the cache shape (plain tweets or
  the `{ kind, tweet, retweet }` feed items that timelines return). Like/retweet/follow use the module-level
  `src/lib/debounced-toggle.ts` (one request for the final state).
- **API access:** browser code uses `src/api/axiosInstance.ts` (cookies, single-flight refresh);
  server components use `src/api/server.ts` (forwards the visitor's cookies). Pages that matter for
  first paint/SEO prefetch on the server and hydrate with `HydrationBoundary`.
- **UI building blocks:** `UserAvatar`, `TweetBody`, `TweetActionButton`, `UserRow`/`UserList`,
  `FeedList` (loading/error/empty states), `PageHeader`, `TabBar`, `SearchBox`, `ConfirmModal`,
  `ImageLightbox`. Reuse them instead of re-creating markup.
- **Colors are theme tokens** (`text-like`, `text-retweet`, `bg-banner`, `text-muted-foreground`, …),
  never raw palette classes like `text-pink-600`. Z-index follows the scale in `globals.css`.
- **UI state that should survive reloads lives in the URL** (profile tabs are routes, search/feed tabs
  and the open DM are query params).
- Icon-only buttons need an `aria-label`. Don't add buttons or links that do nothing.

## Infra conventions

- One `t4g` (arm64) EC2 host runs everything in Docker Compose (`infra/compose/compose.prod.yaml`):
  Caddy (automatic HTTPS; routes `/api/*` to the API, the rest to Next.js, `grafana.<domain>` to
  Grafana), web, api, Postgres (data is disposable) and the monitoring stack. No Redis, RDS or NAT.
- The stack is temporary: `infra/scripts/up.sh` / `down.sh` create and destroy `terraform/app`;
  `terraform/bootstrap` (name servers, GitHub deploy role) is kept. Terraform state is local. The
  user runs `up`, `down` and every `terraform apply` themselves; only do read-only AWS checks.
- A release = one commit SHA: both images plus that commit's `infra/compose` and
  `infra/observability` files (S3). `infra/scripts/deploy.sh` ships it from a laptop or CI; the
  host's `compose/rollout.sh` waits for every health check and rolls back if they fail. So every
  service needs a health check, and configs are mounted as folders and reloaded by `reload-configs.sh`.
- Secrets are generated by Terraform (`random_password`) and stored in SSM under `/chmtwt/`; the
  host renders them into env files at deploy time. Never in user data, git or workflow logs.
- Monitoring is code: alert rules in `infra/observability/prometheus/rules` (SLOs generated by
  `gen_slo_rules.py`), the dashboard by `grafana/gen_dashboard.py`, AWS alarms in
  `terraform/app/alarms.tf`. New metrics worth watching get a panel and, if actionable, a rule
  with a "what to check" section in `infra/observability/README.md`.
- Run `terraform fmt`, `validate` and `test` (mocked provider) for every Terraform change, and
  `shellcheck` for scripts.

## Reviewing or verifying work

1. Read everything in scope before reporting; collect all findings, then fix.
2. Classify each finding: bug, security, dead code, inconsistency, test gap, docs drift.
3. Verify for real: `go vet ./...` + race tests with a test database, web lint/tsc/test/build, and for
   UI changes run the app and look at it (light and dark, desktop and phone width).
