# CLAUDE.md

Guidance for AI assistants (and humans) working in this repo. It's a learning project: follow
mainstream best practices, keep things simple, skip production hardening that doesn't teach anything.

## Repo map

| Path | What |
|---|---|
| `twitter-go-api/` | Primary backend: Go, Gin, PostgreSQL (sqlc, pgvector), Redis. See its README's "Where things live" table. |
| `twitter-next-web/` | Next.js (App Router) frontend: TanStack Query, Tailwind v4, Radix/shadcn primitives. |
| `twitter-java-api/` | Legacy Spring backend. Kept on purpose; being brought to parity with the Go API last. |
| `infra/terraform`, `infra/bootstrap`, `infra/ec2` | AWS as code. **Nothing is deployed**: keep it valid offline, don't plan around a live environment. |
| `docs/MODERNIZATION_PLAN.md` | Findings, decisions and phase checklist. Update it when a phase item lands. |

## Commands

```bash
docker compose up -d                       # Postgres (pgvector, pg16) + Redis for local dev
cd twitter-go-api && make run              # API on :8080, migrations run at startup
cd twitter-next-web && npm run dev         # web on :3000

# Go
make test                                  # go test -race; integration tests need TEST_DATABASE_URL (see README)
make sqlc                                  # after editing internal/db/queries or migrations: regenerates code + MockStore
make swagger                               # after changing handler annotations or DTOs
# Web
npm run lint && npx tsc --noEmit && npm test
# Terraform (no AWS credentials needed)
cd infra/terraform && terraform init -backend=false && terraform validate && terraform test
```

Enable the pre-commit hook once per clone: `git config core.hooksPath .githooks`.

## Go API conventions

- **Package by feature.** `internal/<feature>/service.go` exposes `Service` + `New(...)`, returns domain
  types, never imports Gin. Handlers in `internal/api/` only bind input, call a service and map to a DTO.
- **Every route is in `internal/api/routes.go`**, one line each, with its auth and rate-limit middleware.
- **Interfaces belong to the consumer** (`api/services.go`, or a small private interface in a feature).
- **Errors:** services return `apperr` kinds (`apperr.NotFound`, `Conflict`, …) or wrap DB errors with
  `db.NotFound(err, "thing")`; `api/errors.go` maps them to HTTP. Don't write status codes in services.
- **SQL lives in `internal/db/queries/*.sql`** and is generated by sqlc; never hand-edit `*.sql.go`.
  Lists use keyset cursors (`internal/pagination`), not OFFSET.
- **Schema:** data is disposable, so edit `000001_init_schema.up.sql` in place rather than adding migrations.
- **Auth:** sessions are httpOnly cookies (`access_token`, `refresh_token`) set by the API. Stale
  credentials answer `401 TOKEN_EXPIRED`; no credentials answer `401 UNAUTHORIZED`. Refresh tokens are
  single-use (rotation). Cross-origin writes are blocked by `http.CrossOriginProtection`.
- **Logging:** `slog.InfoContext(ctx, …)` / `ErrorContext`; the request ID is added from `ctx` automatically.
- **Tests:** table-driven; handler tests use the fakes in `api/fakes_test.go`; DB tests use
  `dbtest.OpenTestDB` and skip without `TEST_DATABASE_URL`.

## Web conventions

- **Query keys only from `src/lib/query-keys.ts`.** Never inline key arrays.
- **Optimistic updates go through `src/lib/query-cache.ts`** (`updateTweet`, `updateUser`): one call
  updates every cached copy, whatever the cache shape. Like/retweet/follow use the module-level
  `src/lib/debounced-toggle.ts` (one request for the final state).
- **API access:** browser code uses `src/api/axiosInstance.ts` (cookies, single-flight refresh);
  server components use `src/api/server.ts` (forwards the visitor's cookies). Pages that matter for
  first paint/SEO prefetch on the server and hydrate with `HydrationBoundary`.
- **UI building blocks:** `UserAvatar`, `TweetBody`, `TweetActionButton`, `UserRow`/`UserList`,
  `FeedList` (loading/error/empty states), `PageHeader`, `TabBar`, `SearchBox`, `ConfirmModal`,
  `ImageLightbox`. Reuse them instead of re-creating markup.
- **Colors are theme tokens** (`text-like`, `text-retweet`, `bg-banner`, `text-muted-foreground`, …),
  never raw palette classes like `text-pink-600`. Z-index follows the scale in `globals.css`.
- **UI state that should survive reloads lives in the URL** (profile tabs are routes, search/feed tabs
  and the open DM are query params).
- Icon-only buttons need an `aria-label`. Don't add buttons or links that do nothing.

## Infra conventions

- Production is one EC2 host on one domain: nginx routes `/api/*` to the API and the rest to Next.js
  (`infra/ec2/compose.yml`), certbot renews the certificate. No Redis there; it is only needed to
  scale out to several instances.
- A release = one commit SHA: both images plus that commit's `infra/ec2` files (S3). Change the
  stack by editing `infra/ec2` (shipped by the next deploy); user data only bootstraps the host.
  Every service needs a health check: `deploy.sh` waits for them and rolls back if they fail.
- Alerts are code: AWS alarms in `infra/terraform/alerts.tf`, Grafana rules and the dashboard in
  `infra/grafana`. New metrics worth watching get a panel and, if actionable, a rule.
- Runtime config is SSM parameters under `/<project>/<env>/api/` (one per env var) rendered into
  `api.env` by `infra/ec2/deploy.sh`; secrets never go in user data or workflow logs.
- Run `terraform fmt`, `validate` and `test` (mocked provider) for every Terraform change.

## Reviewing or verifying work

1. Read everything in scope before reporting; collect all findings, then fix.
2. Classify each finding: bug, security, dead code, inconsistency, test gap, docs drift.
3. Verify for real: `go vet ./...` + race tests with a test database, web lint/tsc/test/build, and for
   UI changes run the app and look at it (light and dark, desktop and phone width).
