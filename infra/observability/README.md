# Monitoring

Metrics, logs, a dashboard and alerts for the site. The same configuration runs on your machine
and on the AWS host, next to the app.

| Tool | What for | Local | Production |
|---|---|---|---|
| Grafana | Dashboard "Twitter overview", Explore | http://localhost:3001 | `https://grafana.<domain>` (user `admin`) |
| Prometheus | Metrics, alert rules | http://localhost:9090 | internal only |
| Alertmanager | Grouping, silences, Discord | http://localhost:9093 | internal only |
| Loki + Alloy | Logs of every container | via Grafana | via Grafana |

## Run it locally

```bash
docker compose --profile observability up -d   # from the repo root
cd twitter-go-api && make run                  # Prometheus scrapes it on host.docker.internal:8080
docker compose --profile observability stop prometheus alertmanager loki alloy grafana
```

Locally Alloy collects only containers' logs (Postgres, the monitoring stack); the API you run
with `make run` logs to your terminal. Try the whole production stack on your machine with
[`../compose/README.md`](../compose/README.md).

## What is collected

**Metrics** (scraped every 15 s)

| Source | Metrics |
|---|---|
| API (`api:8080/metrics`) | `http_requests_total{method,path,status}`, `http_request_duration_seconds{method,path}` (path is the route pattern, e.g. `/api/v1/users/:id`), `embedding_jobs{state}`, `embedding_jobs_processed_total{result}`, Go runtime |
| Caddy (`caddy:9180`) | `caddy_http_request_duration_seconds{host,code,method}`: every request to the site, pages included |
| Node Exporter | Host CPU, memory, swap, disk |

**Logs** (Loki): every container, labelled `service` (compose service name). The API (slog) and
Caddy write JSON; their `level` is a label (`info`, `warn`, `error`). Caddy passes its request
ID to the API as `X-Request-ID`, so one ID finds a request in both.

```logql
{service="api", level="error"}
{service="api"} | json | status >= 500
{service="caddy"} | json | status >= 500 | line_format "{{.request_uri}} {{.status}}"
sum by (service) (count_over_time({level="error"}[5m]))
```

## Dashboard

Built by [`grafana/gen_dashboard.py`](grafana/gen_dashboard.py) (edit the panels there, then run it;
CI checks the JSON is up to date): SLOs and error budget, site traffic (Caddy), API traffic by
route and the slowest routes, the embedding queue, Go runtime, host, and recent API errors.

## Alerts

Rules live in [`prometheus/rules`](prometheus/rules). Alertmanager groups them and posts to Discord.

**SLOs** (generated by [`prometheus/gen_slo_rules.py`](prometheus/gen_slo_rules.py): edit the table,
run it, `curl -X POST localhost:9090/-/reload` locally):

| SLO | Good requests | Objective |
|---|---|---|
| API availability | not 5xx | 99.5% |
| API latency | answered within 500 ms (event streams excluded) | 99% |

Health checks and `/metrics` don't count. Each SLO gets a **fast burn** alert (severity `page`:
the error budget is going 14.4× too fast over 1 hour, or 6× over 6 hours) and a **slow burn** alert
(`ticket`: 3× over a day, or 1× over 3 days). Each also checks a short window, so it stops firing
soon after the problem is fixed. While the page fires, Alertmanager holds back the ticket for the
same SLO. Burn-rate alerts react to how much of the error budget is being spent, so a few errors
on a quiet night don't page while a real outage does within minutes.

**Other alerts** ([`prometheus/rules/service.yml`](prometheus/rules/service.yml)): `ApiDown`,
`SiteErrors` (over 5% of all requests are 5xx, pages included), `DiskAlmostFull`,
`MemoryAlmostFull`, `EmbeddingJobsFailing`, `EmbeddingBacklog`.

**AWS** (by email, [`../terraform/app/alarms.tf`](../terraform/app/alarms.tf)): the host failing
a status check (recovered or rebooted automatically), high CPU, and the monthly budget. They cover
what this stack can't report about itself: the host being down.

### Discord

1. In Discord: a server you own → a channel such as `#alerts` → **Edit Channel → Integrations →
   Webhooks → New Webhook → Copy Webhook URL**.
2. Production: `discord_webhook_url` in `infra/terraform/app/terraform.tfvars`, then
   `infra/scripts/up.sh` (Terraform stores it in SSM; each deploy writes it to the host).
3. Locally: `pbpaste > infra/observability/alertmanager/secrets/discord_webhook_url` (git-ignored),
   then send a test alert:
   ```bash
   docker compose exec alertmanager amtool alert add Test severity=ticket \
     --annotation='summary="Test alert"' --alertmanager.url=http://localhost:9093
   ```

Treat the webhook URL as a password: anyone with it can post to the channel.

## What to check when an alert fires

### API availability

Some API requests answer 5xx. In the dashboard's "5xx / s" panel: one route or all of them? Then
`{service="api", level="error"}` in Explore. All routes failing usually means the database
(`{service="postgres"}`, `/readyz`); one route usually means a bug in that handler or an outside
service (Gemini, S3).

### API latency

More than 1% of requests take over 500 ms. "Slowest routes (p95)" shows whether it's one route (a
slow query: check its SQL and indexes) or all of them (the host: CPU, memory, swap in the Host row).

### API down

Prometheus can't scrape the API. On the host: `dc ps` and `dc logs --tail 50 api`
([`../README.md`](../README.md#on-the-host)). A failing `/readyz` usually means Postgres is down.

### Site errors

Caddy answers 5xx for more than 5% of requests, pages included. A 502 means the web app or the
API isn't answering Caddy: `dc ps`, then the logs of the one that isn't healthy.

### Disk or memory

`df -h` and `docker system df` on the host. Old images are pruned on each deploy; Prometheus keeps
15 days and Loki 14. Memory: `docker stats` shows which container grew.

### Embedding queue

`failed` jobs gave up after every retry: `SELECT tweet_id, attempts, last_error FROM embedding_jobs
WHERE attempts >= 8` (`dc exec postgres psql -U twitter`). A growing `pending` backlog usually means
Gemini is down or out of quota (the API's warnings say which).
